## 当前探针的观测盲区

## 单规则诊断 v2：只补执行位置标记

更新同一份 [单规则插件](https://raw.githubusercontent.com/ccyykk666/Loon-Plugin/main/plugins/qqmusic/qqmusic_single_rule_diagnostic.lpx)，改用新的 [执行位置探针](https://raw.githubusercontent.com/ccyykk666/Loon-Plugin/main/plugins/qqmusic/qqmusic_request_guard_trace.js)。仍只有一条规则、相同匹配范围和选项、相同 zlib 库及请求筛选逻辑，不初始化响应解码库，不修改正文或业务字段。原阶段 12 的脚本及累计诊断文件不变。

新 Tag 为 `QQM-Single-GuardTrace`。每次运行按执行位置输出：

1. `ENTRY`：用户 JavaScript 第一段顶层代码已执行，位于库初始化之前。
2. `CODEC_READY`：请求解码库初始化已返回。
3. `BODY_READY`：读取 `$request.body` 已返回，尚未解压/解析。
4. `GUARD_READY`：筛选流程已返回，附非敏感的结果、类型和长度。
5. `CALL_DONE`：定时器回调已进入，即将调用 `$done({})`。

`elapsed_ms` 从入口开始计时，`step_ms` 为相邻标记时间差；两者包括其间日志开销。入口标记不读取请求、响应或 `$script` 上下文，计时也不覆盖用户 JavaScript 开始前的工作。使用的日志、定时器及完成回调见 [Loon Script API](https://nsloon.app/docs/Script/script_api/)。

记录的是执行到达位置；最后出现的标记不能单独证明紧接着的某一条指令就是根因。`CALL_DONE` 也不等于原生层已经完成结果交付。完全没有入口输出时，仍可能涉及用户代码开始前的工作或日志不可用。增加日志会影响执行，本轮用于定位，不作为无扰动的性能基准。

测试仍先禁用原网络诊断和去广告插件，只保留更新后的单规则诊断；手动重启一次 Loon 连接，先抓包再重开 QQ 音乐约 30 秒。除了 HAR，需要卡顿期间任意一条新 Tag 任务的完整脚本日志，直接从任务列表选取即可，无需按 HAR 毫秒时间或编号配对。日志中即使没有任何 TRACE，也应保留原生接收/完成信息。
