# QQ 音乐阶段 6 捕获分析（2026-10-17）

环境：用户报告 QQ 音乐 20.9.0、Loon 3.5.3（1008）。阶段 0 仅 MITM 时正常，阶段 1 和阶段 6 均报告加载慢。以下统计来自用户随后提供的阶段 6 HAR；不公开原始 HAR、请求正文、Header、账号或凭据。

## 已确认的现象

阶段 6 规则匹配两个主机的聚合 JSON POST 请求，脚本仅包含：

```javascript
$done({});
```

这个返回值按 [Loon 官方文档](https://nsloon.app/docs/Script/script_api/#112-放行原请求或响应) 表示不修改请求或响应。脚本没有参数读取、正文处理、解压、日志、网络请求或异步等待。规则配置的执行超时为 5 秒，这不代表 HAR 总耗时等于脚本耗时。

捕获中请求开始时间范围为 **17:24:54.532 至 17:25:10.862（UTC+8）**，共 514 条；该范围不包含最后一条请求的完整结束时间。

| 统计项 | 条数 | 解释 |
| --- | ---: | --- |
| 带 `QQM-D6-Noop` 匹配标记 | 198 | 包含 1 条仅记录请求头、尚活跃的请求 |
| 日志明确记录触发 Request Script | 197 | 其余 1 条不能计为已执行 |
| 记录 `Evaluate script timeout` | 90 | 一行放行脚本所在的执行过程也出现超时 |
| HTTP 200 | 25 | 24 条无超时日志；1 条超时后继续发往上游并成功 |
| 客户端 `Left stream RST:8`，且无上游发送日志 | 172 | 均为 HTTP status 0，不能当作服务器返回错误 |
| 请求/响应修改标记为 true | 0 | 所有匹配记录均未标记修改 |

198 条的结果分解为：25 条 HTTP 200、172 条客户端重置、1 条捕获时仍活跃。90 条超时与重置存在重叠，不能把这两列相加。

全部捕获里的 Script 标记只有 `QQM-D6-Noop`。这没有证明全局配置里不存在其他未命中规则，但没有发现该窗口内其他脚本实际触发。

## 最有说明力的一条请求

HAR 条目索引 311（从 0 开始）、Loon recordId 11444，开始于 17:24:58.180，总耗时 7417 ms，日志顺序为：

```text
Trigger http-request script:QQM-D6-Noop
Script evaluate timeout in http-request script:QQM-D6-Noop (Evaluate script timeout.)
Reuse connection:354
Send request header
Send request body finished
Receive response header
Receive response body finished
```

最终 HTTP 状态为 200。因此，这条请求的脚本超时发生在日志记录上游发送之前；服务器仍能处理放行后的请求。7417 ms 是整条请求的耗时，不能直接当成 JavaScript 的执行时间。

## 取消与超时的先后关系

90 条超时记录中：83 条的日志把超时追加在客户端重置之后，6 条先记录超时再记录客户端重置，1 条超时后发往上游并成功。

因此不能说“90 次超时全都导致客户端取消”，也不能说“所有取消都由脚本超时引起”。可以确认的是：大量请求在本地脚本处理期间没有进入日志所示的上游发送流程，同时伴随脚本超时和客户端取消。HTTP/2 的错误码 0x8 表示 CANCEL，见 [RFC 9113 第 7 节](https://www.rfc-editor.org/rfc/rfc9113#section-7)；它本身不说明应用为什么取消。

异常具有突发并发背景：按请求开始时间计算，最密集的 1 秒窗口内有 79 条已触发脚本的请求开始，最密集的 100 ms 窗口内有 21 条。窗口不是互不重叠的自然秒分桶；这些数字是请求到达量，不是 JS 引擎同时运行数量，不能据此推断具体并发上限。

## 结论与仍待验证的部分

本次已经确认请求脚本执行过程的超时问题，无需广告数据改写或 Brotli/zlib 解压即可复现；研究重点应转向 Loon 的脚本调度、完成/取消处理和网络请求恢复过程。没有足够证据把具体机制定性为 Loon 1008 已知缺陷。

这份记录没有明确的证书/握手错误日志；配合阶段 0 正常的用户对照，不支持把本次最小复现直接归因为 IPA 全面禁止 MITM。未发送的这些请求也不能用“服务器校验广告响应失败”解释。应用的其他连接或证书校验路径仍应分别判断。

HAR 没有隧道重启、系统内存终止或完整运行时诊断证据，因此自动重连原因尚未确认。

下一步只新增阶段 7：把同一个一行放行文件放到响应头阶段，保持主机、路径、JSON Header 过滤和超时设置。根据 [Loon 的执行阶段定义](https://nsloon.app/docs/Script/script_v2/)，它在响应头到达后执行，不再提前阻挡本插件所匹配的上游请求。阶段 7 不读取正文，不修改数据，不能视为修复版或恢复去广告功能。

若阶段 7 正常，优先调查请求阶段或该阶段的并发模式；若阶段 7 也出现执行超时，优先调查共同的运行时、调度与资源管理。两种结果都需要新 HAR 核实，正常响应到达会改变并发节奏，不能把它作为单变量的底层缺陷证明。
