# QQ 音乐阶段 7 捕获分析（2026-10-17）

环境仍为用户报告的 QQ 音乐 20.9.0、Loon 3.5.3（1008）。阶段 7 使用与阶段 6 相同的 `$done({});` 文件，仅把执行位置移到 HTTP 200 响应头阶段，不读取正文、不修改业务数据。用户反馈“前面卡了很久，后面好像正常了”。

以下仅公开汇总统计及不含凭据的日志字段，不公开 HAR、请求正文、账号、Cookie 或 Token。

## 捕获到的结果

捕获共 720 条请求，请求开始时间范围为 17:29:35.633 至 17:30:15.576（UTC+8）。全文件仅有 `QQM-D7-ResponseHeaderNoop` 一个 Script Tag。

| 阶段 7 匹配记录 | 数量 |
| --- | ---: |
| 明确触发响应脚本 | 221 |
| HAR 记录 HTTP 200 | 221 |
| 日志记录上游发送，且 `Right stream closed:0` | 221 |
| `Evaluate script timeout` | 56 |
| 客户端 `Left stream RST:8` | 57 |
| 有下游 `Receive response body finished` 完成日志，且无重置 | 164 |
| 请求或响应被标记修改 | 0 |

56 条超时均与重置重叠；另外 1 条重置未记录超时。它们不能与 164 条完整完成记录重复相加。所有超时日志均追加在客户端重置之后，不能断言超时必然先于并导致这些取消。

这里的 HTTP 200 只证明捕获到了上游状态，不代表 QQ 音乐已收到完整响应。57 条重置记录没有下游正文完成日志，不能按“HTTP 200 成功率 100%”判断应用加载成功。

## 上游连接关联

日志里复用上游连接 `33` 的 67 条阶段 7 请求中，55 条超时并重置，12 条完成。稍后复用上游连接 `544` 的 100 条则全部完成，无超时或重置。

这两组都是 `u6.y.qq.com`，且 HAR 的客户端 tunnelId 同为 `19`；变化的是日志所示的上游复用连接，不是证据充分的 VPN 隧道重启。另有 1 次超时发生在不同的上游连接，因此不能声称异常仅存在于连接 33。

这是连接状态与异常的相关性。负载、时间和请求内容也在变化，不能认定换连接就是恢复的原因，更不能把两个连接编号当成系统错误码。

## 压缩、JSON 与业务结果

离线使用标准 JSON、Brotli/zlib 解码路径检查了全部 221 条捕获响应，均能解析成 JSON，顶层 `code` 均为 0；57 条重置记录也如此。部分子请求存在非零业务状态，正常完成组和重置组都存在，不能把顶层 0 当成每个子业务都成功。

这些检查仅在本地离线执行；阶段 7 的手机脚本本身没有读取、解压或解析这些正文。当前最小复现不需要修改广告数据或加入额外解密。

## 当前判断

1. 请求阶段与响应阶段的一行脚本都伴随执行超时，不能把问题限定为 Request Script 或旧版解压代码。
2. 响应阶段的异常发生在上游已返回 HTTP 状态之后，重点应放在 Loon 脚本执行/完成/取消处理，以及 HTTP/2 流和连接状态的交互。
3. 阶段 0 正常的用户观察，加上阶段 7 能捕获并解析上游响应，不支持直接归因为整个 IPA 禁止 MITM。不能据此保证其他接口或认证分支都兼容。
4. 日志没有明确证书、握手或系统内存终止证据。另有 23 条其他记录出现 `Session closing...`；这不等于已经证实 VPN 自动重连。HAR 本身不足以确定隧道进程为什么重启。
5. 具体是调度、并发、完成回调、取消清理还是连接复用问题，仍未确认；也没有可靠依据称其为 Loon 1008 已知缺陷。

## 下一项对照

不更新插件、不增加新阶段。保持阶段 7 和当前 Loon 连接，只彻底退出并重新启动 QQ 音乐，抓取启动前后约 30 秒。

如果再次集中出现同样超时/重置，支持继续调查应用启动时的负载和新建连接过程；如果仍正常，则支持进一步区分 Loon 冷启动、连接状态或缓存的影响。两种结果都不构成某个底层原因的单独证明。需要更具体的运行时原因时，应提供覆盖异常前后的 Loon 运行日志；不公开主配置的凭据或证书私钥。

原去广告插件继续保持停用，阶段 7 的后期改善不能作为恢复业务改写的验证。
