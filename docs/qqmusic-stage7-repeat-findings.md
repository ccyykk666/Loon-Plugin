## 对既有假设的影响

启动时集中异常、随后恢复的行为已在两份阶段 7 捕获中重复出现。按上一步实验条件执行的用户反馈，使“只在第一次启动 Loon 时有一次初始化问题”的解释变弱，但没有排除每次新建网络连接或应用启动负载带来的影响。

尚不能确认具体底层原因。请求/响应头阶段都可出现一行脚本超时，当前继续调查完成路径与 HTTP/2 流的取消、恢复处理，比增加广告字段改写更有依据。

## 下一项仅改变完成方式

诊断 v4 新增阶段 8：保留阶段 7 的响应头匹配条件、主机、5 秒超时和原样放行结果，改用以下文件：

```javascript
setTimeout(function () {
  $done({});
}, 0);
```

它不读取或修改请求/响应，不输出日志，不解压，也不发起网络请求。零延时是定时器的请求值，不保证实际执行无等待。`setTimeout` 是 [Loon 官方提供的 API](https://nsloon.app/docs/Script/script_api/#22-settimeoutcallback-delay-args)。

目的仅是比较同步调用完成与定时器回调完成的行为，检查完成时机是否影响复现；没有证据证明当前存在同步回调竞态，也不能把异步写法宣传为修复。脚本初始化、排队、连接状态等仍可能影响两种写法。

如果阶段 8 仍异常，记录其超时、取消和关闭情况，不继续把同一完成方式假设当作已获支持。如果改善，则需重复启动核实，不能仅凭一次好转恢复原去广告插件。阶段 8 最初提供时只有本地定时器与放行检查，随后已取得下述真机捕获。
