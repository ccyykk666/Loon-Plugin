## 单规则 v3：只取消最后的定时器

当前关注点转到筛选完成之后的交接。新建 [同步完成探针](https://raw.githubusercontent.com/ccyykk666/Loon-Plugin/main/plugins/qqmusic/qqmusic_request_guard_trace_sync.js)，保留 v2 的库代码、筛选逻辑、匹配范围、正文选项、五秒超时及五处日志；只将末尾的零延时定时器改为直接调用 `$done({})`。日志前缀改为 `QQM-TRACE-v2-sync`，最后一个标记为 `CALL_DONE_SYNC`；其余四个标记及日志字段保持相同。

同一份 [单规则插件](https://raw.githubusercontent.com/ccyykk666/Loon-Plugin/main/plugins/qqmusic/qqmusic_single_rule_diagnostic.lpx) 更新至诊断 v3，Tag 为 `QQM-Single-GuardTraceSync`。异步探针原文件及阶段 0 至 12 文件保留不变，便于复核。

这不是将“同步完成一定正常”当作结论。此前阶段 6、7 的同步空脚本也出现过超时；但它们与当前的请求筛选、正文阶段及日志不相同。当前是在两个具体实例都出现末段长间隔之后，保留其余处理进行完成时机对照。官方允许同步操作完成后直接调用 `$done`，本探针没有需要等待的 HTTP 或其他异步操作。

- 若同步末段也有较大间隔，说明定时器不是该间隔的必要条件，继续检查日志写入、线程暂停等。
- 若末段间隔消失且捕获改善，只能支持最后的完成方式参与问题，仍需复核稳定性；不能凭一条短日志认定修复。
- 若末段间隔消失但仍有超时，需要进一步定位入口前工作或完成提交之后的交付等环节，不能将直接调用等同于原生完成。

保持旧网络诊断和去广告插件禁用，更新现有单规则插件，只启用这一份；手动重启一次连接，先抓包再重开 QQ 音乐约 30 秒。回传 HAR 与卡顿期间任意一条新 Tag 的完整脚本日志，不要求按请求时间或任务编号匹配。

本地对本轮 184 条真实匹配请求检查了同步/异步两版的筛选结果一致、五处标记顺序、输入字节不变，以及同步版不注册定时器、只提交一次空结果；另检查了缺失、畸形正文与日志不可用时的放行。源文件对比确认除了版本标记和末尾完成方式外代码一致。同步版尚待 Loon 3.5.3(1008) 真机验证。
